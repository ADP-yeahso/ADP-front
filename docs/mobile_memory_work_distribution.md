# 모바일 정원 메모리 개선 — 3인 업무 분배

작성일: 2026-10-03  
대상: main-home의 나무·꽃 정원 화면 (`GardenScreen`, Three.js WebView)  
목적: 카메라 구도와 디자인을 유지하면서 메모리 잔류, 로딩 중 최대 사용량, 불필요한 재생성을 줄인다.

이 문서는 앞으로 진행할 작업의 분배안이다. 아래 신규 파일과 API는 제안이며 아직 구현되지 않았다. 디자이너의 GLB 재제작과 개발자의 메모리 개선은 별도로 진행한다.

## 1. 담당자별 요약

| 담당자 | 담당 영역 | 주요 결과물 | 권장 브랜치 |
|---|---|---|---|
| 담당자 A | Three.js 자원 해제·렌더러 수명 관리·JS 통합 | 자원 해제 모듈, 활성/종료 API, 통합된 main.js | `feature/garden-resource-lifecycle` |
| 담당자 B | GLB 로딩·모델 재사용·캐시 관리 | 로딩 큐, 취소 처리, 사용량 제한 캐시 | `feature/garden-model-loading` |
| 담당자 C | Flutter 화면 수명 관리·모바일 측정·에셋 협업 | 탭/앱 상태 연결, 초기화 안전성, 측정 보고서 | `feature/garden-mobile-lifecycle` |

공통 우선순위는 **자원 해제 누락 수정 → 로딩 동시성 제한 → 모델 복사·재파싱 감소 → 비활성 화면 관리 → 실기기 측정**이다.

### 현재 이미 반영된 개선

- 필요한 꽃 종류만 로드하고 같은 종류는 `InstancedMesh`로 표시한다.
- DPR은 최대 2로 제한한다.
- 화면이 변하거나 OrbitControls 감쇠가 진행될 때 렌더링한다.
- `gardenLoadId`로 이전 월의 결과가 현재 화면에 추가되는 것을 막는다.
- GLB는 HTTP 캐시를 사용한다.

이 기능은 유지한다. 이전 월 결과를 무시하는 것과 진행 중인 로딩을 취소하는 것은 다르며, HTTP 캐시와 파싱된 모델 캐시도 구분한다.

## 2. 파일 소유권과 공통 인터페이스

현재 로딩·자원 해제·렌더링이 `assets/www/main.js`에 모여 있다. 세 사람이 이 파일을 동시에 대규모 수정하면 충돌이 잦으므로, A가 공통 연결부를 담당하고 B는 별도 모듈을 만든다.

| 파일 | 수정 책임 |
|---|---|
| `assets/www/main.js`, 필요 시 `assets/www/index.html` | A가 최종 연결·통합. B/C는 필요한 연결 변경을 A에게 전달 |
| `assets/www/garden_resources.js` (신규 제안) | A: 자원 해제와 렌더러 수명 관리 |
| `assets/www/garden_loader.js` (신규 제안) | B: 로딩 큐와 요청 세대 관리 |
| `assets/www/garden_model_cache.js` (신규 제안) | B: 모델 템플릿 재사용과 사용량 제한 |
| `lib/screens/garden/garden_screen.dart` | C: WebView 초기화·종료·활성 상태 연결 |
| `lib/screens/root_shell.dart` | C: 정원 탭의 활성 상태 전달 |
| `lib/utils/local_asset_server.dart` | C: 서버 수명·캐시 버전 관련 수정이 필요한 경우 |
| `docs/mobile_memory_validation.md` (신규 제안) | C가 작성, A/B가 측정 자료 제공 |
| `docs/flower_asset_review.md`, `assets/www/flower_catalog.json` | C가 디자이너 납품 후 수치 재측정·갱신 |

### 착수 전에 합의할 API

| API | 계약 | 구현 책임 |
|---|---|---|
| `window.initGarden(treeUrl, flowerMapJson, diariesJson, assetPreview = false)` | 기존 호출 형식 유지. 최신 요청만 현재 장면을 변경 | A 연결 / B 로딩 |
| `window.disposeGarden()` | 월 데이터의 인스턴스 정리 및 기존 요청 무효화. renderer와 재사용 중인 나무까지 매번 종료하지 않음 | A/B |
| `window.setGardenActive(active)` | 비활성 시 새 렌더·애니메이션과 불필요한 로딩을 멈춤. 활성 복귀 시 필요한 상태를 복원 | A 구현 / C 호출 |
| `window.shutdownGarden()` | 화면 완전 종료용. 요청·캐시·장면·renderer·controls·이벤트·예약 프레임을 정리. 중복 호출에도 안전 | A 구현 / B 캐시 해제 / C 호출 |

`disposeGarden()`의 의미를 바꾸므로 Flutter의 월 전환 호출과 브라우저 미리보기의 호출을 함께 확인한다. 새로 나무를 추가하기 전에 기존 나무를 재사용할지 교체할지 A/B가 명시적으로 결정한다.

JavaScript 준비 완료와 종료 완료는 `FlutterChannel`의 전용 메시지(예: `GARDEN_READY`, `GARDEN_SHUTDOWN_COMPLETE`)로 전달하는 방안을 A/C가 합의한다. 이 메시지와 `ERROR_*`를 일기 ID로 처리하지 않도록 Flutter 분기에서 구분한다. 기존 나무·꽃 탭 메시지는 유지한다.

### 공유 자원의 소유권

- B의 캐시가 재사용할 geometry·material·texture와 모델 템플릿을 소유한다.
- A가 만드는 인스턴스는 해당 템플릿을 빌려 사용한다. 제거 시 인스턴스 전용 버퍼를 해제하고 캐시의 사용 참조를 반환한다.
- 사용 중인 템플릿은 캐시에서 제거하거나 dispose하지 않는다. 마지막 사용자가 해제한 뒤에만 캐시 정책에 따라 정리한다.
- A의 자원 해제 도구를 B가 캐시 퇴출 시 호출한다. 공유 자원과 인스턴스 전용 자원의 해제 경로를 구분한다.
- 텍스처가 공유하는 `ImageBitmap`도 마지막 사용자가 해제된 뒤에 닫는다. 원본 모델을 정리하면서 화면에서 사용 중인 텍스처까지 제거하지 않는다.

## 3. 담당자 A — 자원 해제와 렌더러 수명 관리

**목표:** 반복 월 전환과 화면 종료에서 불필요한 GPU/이미지 자원이 남지 않게 한다.

### 할 일

- [ ] 현재 `disposeObject3D()`와 `disposeGarden()`을 월 데이터 정리와 완전 종료로 분리한다.
- [ ] `InstancedMesh.dispose()`를 호출해 인스턴스 행렬·색상 GPU 버퍼의 해제 경로를 실행한다.
- [ ] 공유 geometry·material·texture는 사용 참조를 반환하고, 소유한 자원만 실제로 해제하도록 정리한다.
- [ ] `ImageBitmap` 사용 여부를 확인하고 마지막 사용 시 `close()` 처리한다. 일반 HTML 이미지에는 적용하지 않는다.
- [ ] 중복 해제와 재호출이 안전하도록 상태를 관리한다.
- [ ] 예약한 `requestAnimationFrame` ID를 관리해 비활성/종료 시 취소한다.
- [ ] GSAP 애니메이션, controls, window 이벤트를 완전 종료 시 해제한다. 익명 이벤트 핸들러는 제거할 수 있도록 관리한다.
- [ ] 완전 종료 시 나무·꽃·바닥·그림자 관련 자원과 renderer를 정리한다. 월 변경마다 renderer를 파괴하지 않는다.
- [ ] `setGardenActive()`와 준비/종료 메시지를 구현하고 C와 연결한다.
- [ ] B의 로더·캐시를 main.js에 연결하고 기존 카메라·줌·꽃/나무 탭 동작을 보존한다.

### 완료 기준

- 같은 정리를 두 번 호출해도 오류가 없고, 사용 중인 공유 텍스처가 사라지지 않는다.
- 월 전환 후 현재 장면의 인스턴스 수가 현재 데이터와 일치한다.
- 동일한 월로 반복 복귀했을 때 geometry·texture 수가 계속 증가하지 않는다.
- 완전 종료 후 새 로딩 결과가 장면을 다시 만들거나 렌더링을 예약하지 않는다.
- 시뮬레이터에서 원래 카메라 구도와 전체 꽃 미리보기가 유지된다.

### B/C에게 전달할 것

- 자원 해제 도구의 사용법과 공유 자원 해제 규칙.
- 활성/종료 API와 전용 채널 메시지.
- 종료 전후 geometry·texture·인스턴스 수 및 예약 작업 상태.

## 4. 담당자 B — 로딩 큐와 모델 재사용

**목표:** GLB 파싱·이미지 디코딩이 한꺼번에 겹치는 것을 줄이고, 월 이동 시 같은 모델의 재생성을 최소화한다.

### 할 일

- [ ] 현재 `uniqueUrls.map()` + `Promise.all()` 로딩을 동시성 제한 큐로 교체한다. 초기 동시 처리 수는 2~3개로 하고 측정 후 조정한다.
- [ ] 취소 단위는 월 요청으로 둔다. 이전 월의 대기 작업을 제거하고 현재 월만 장면에 반영한다.
- [ ] 가능하면 파일 요청도 취소한다. GLTFLoader의 모든 디코딩 작업이 중간 취소 가능한 것으로 가정하지 않는다.
- [ ] 이미 진행 중인 작업이 취소 불가능하면 완료 직후 소유권 규칙에 따라 정리하고, 새 작업 시작 전에 요청 세대를 확인한다.
- [ ] 일부 파일 실패 시 성공한 모델을 표시하거나 정리하는 명시적 정책을 만든다. 한 종류 실패 때문에 나머지 자원이 방치되지 않게 한다.
- [ ] 같은 URL의 동시 로딩을 하나의 작업으로 합친다. 한 월의 취소가 다른 사용자의 공유 작업을 잘못 취소하지 않게 한다.
- [ ] geometry·material을 매월 복사하지 않도록 모델 템플릿을 재사용한다. 좌표 변환을 geometry에 반영해야 한다면 템플릿 제작 시 한 번만 처리한다.
- [ ] 나무는 월 간 재사용하고 꽃의 인스턴스 개수·행렬·일기 매핑만 필요한 만큼 갱신한다.
- [ ] 캐시에 사용 참조와 퇴출 정책을 둔다. 현재 사용 중인 모델은 보호하고 미사용 모델부터 제거한다.
- [ ] 캐시 예산은 파일 크기만으로 판단하지 않는다. geometry 배열과 텍스처 해상도의 추정 사용량을 기록하고 실제 기기 결과로 한도를 정한다.
- [ ] URL의 에셋 버전이 바뀌면 새 템플릿으로 교체할 수 있게 한다. 개발 중 교체한 GLB가 예전 캐시로 보이지 않도록 C와 버전 정책을 맞춘다.

### 완료 기준

- 동시에 진행하는 모델 처리 수가 설정한 상한을 넘지 않는다.
- 월을 빠르게 바꿔도 마지막 선택한 월만 표시된다.
- 파일 하나의 실패·이전 월 취소·동일 파일의 중복 요청에서 자원 소유권이 유지된다.
- 같은 월로 다시 돌아올 때 재사용된 모델과 새로 파싱한 모델의 수를 구분해 확인할 수 있다.
- 캐시가 무제한 증가하지 않고 사용 중인 모델을 잘못 해제하지 않는다.

### A/C에게 전달할 것

- 로더/캐시 모듈과 최소 연결 예제. main.js 전체를 별도 구현으로 교체하지 않는다.
- 작업 취소·참조 반환·캐시 퇴출 계약.
- 동시 로딩 수, 대기 수, 파싱 횟수, 캐시 적중·퇴출 수, 추정 사용량 로그.

## 5. 담당자 C — Flutter 화면 관리와 모바일 검증

**목표:** 정원이 보이지 않을 때 작업을 억제하고, 기기에서 개선 전후를 비교할 수 있게 한다.

### 할 일

- [ ] RootShell의 현재 탭을 GardenScreen에 전달하고 정원 활성 여부를 JavaScript와 연결한다.
- [ ] `WidgetsBindingObserver` 등으로 앱의 전경/백그라운드와 메모리 압박 상태를 처리한다.
- [ ] 초기에는 탭 이탈 시 일시 중지만 적용한다. 장시간 이탈/메모리 압박 시 자원 해제와 복귀 로딩 정책은 측정 후 결정한다.
- [ ] IndexedStack을 유지하면 비활성 정원의 메모리가 남는다는 점을 측정에 반영한다. 가려진 화면이 자동으로 dispose된다고 가정하지 않는다.
- [ ] 비동기 서버 시작 중 화면 종료, 초기화 실패, 중복 시작에서 `late` 컨트롤러 접근과 서버 잔류를 막는다.
- [ ] HTML의 `onPageFinished`와 JS 모듈의 준비 완료를 구분한다. 재시도 타이머가 화면 종료 후 계속되지 않도록 한다.
- [ ] 완전 종료 시 JS 정리 완료와 WebView 제거를 연결한다. `dispose()`에서 비동기 정리가 항상 끝날 것으로 가정하지 않고, 명시적인 종료 흐름과 실패 시 정리 경로를 만든다.
- [ ] FlutterChannel의 준비/종료/오류 메시지를 일기 ID와 구분하고, 활성 복귀·오류 상태의 UI를 처리한다.
- [ ] 에셋 버전 갱신 절차와 테스트 실행 방법을 문서화한다. CDN 의존 제거는 A와 협의해 별도 변경으로 진행한다.
- [ ] 디자이너에게 `flower_asset_review.md`의 대상과 목표를 전달할 자료를 준비하고, 납품된 GLB의 삼각형·용량·파트·텍스처 해상도를 재측정한다.
- [ ] 실제 Android/iPhone에서 공통 시나리오를 실행하고 `mobile_memory_validation.md`에 결과를 기록한다.

### 완료 기준

- 정원 비활성/앱 백그라운드 상태에서 새 애니메이션·불필요한 로딩이 시작되지 않는다.
- 복귀 후 일기와 꽃 매핑, 월 선택, 카메라 동작이 정상이다.
- 초기화 중 종료하거나 로그아웃 후 재진입해도 서버·WebView·JS 관련 오류가 없다.
- Flutter 측 메모리만으로 결론 내리지 않고 WebView/WebContent 측 사용량도 함께 확인한다.
- 기기·OS·빌드 모드·꽃 개수·실행 절차가 포함된 개선 전후 보고서를 만든다.

## 6. 병렬 진행과 통합 순서

1. **공통 준비:** 동일한 기준 커밋에서 브랜치를 나눈다. C는 기준 성능을 먼저 기록하고, A/B는 API와 공유 자원 소유권을 합의한다.
2. **짧은 기반 작업:** A가 자원 해제/렌더러 관리 코드를 모듈로 분리하고 인터페이스를 확정한다. 동작 변경은 최소화한다. B는 이때 로딩 모듈을 독립적으로 작성하고 C는 Flutter 수명 처리를 시작할 수 있다.
3. **병렬 구현:** A는 해제·활성/종료 API, B는 로딩 큐·캐시, C는 Flutter 연결·측정 환경을 진행한다. 기반 변경이 합쳐지면 각 브랜치에 반영한다.
4. **1차 통합:** A의 자원 해제를 먼저 합치고 B의 로딩 큐를 연결한다. 캐시 재사용은 해제 규칙을 확인한 뒤 합친다.
5. **2차 통합:** C의 탭/앱 상태 처리를 연결하고 일반 앱과 별도 꽃 미리보기 진입점을 모두 확인한다.
6. **검증:** C가 공통 시나리오를 실행하고 A/B가 담당 영역의 실패를 수정한다. 에셋 교체 전후 측정은 코드 변경 효과와 구분한다.

공유 파일 수정이 필요하면 담당자와 먼저 범위를 합의한다. 다른 사람의 파일을 통째로 덮어쓰거나 동일 기능의 별도 구현을 main.js에 추가하지 않는다. PR에는 변경 목적·검증 결과·메모리 소유권 변경을 기록한다.

## 7. 공통 검증 시나리오

실기기는 팀이 지원할 Android와 iPhone을 선정한다. 시뮬레이터는 화면·동작 확인에 사용하며 모바일 메모리/발열의 최종 합격 근거로 사용하지 않는다. 빌드 모드는 개선 전후 동일하게 맞추고, 성능 비교는 실제 기기의 profile 또는 release로 진행한다.

| 시나리오 | 절차 | 확인할 것 |
|---|---|---|
| 첫 진입 | 꽃 0/30/60/100송이, 동일한 고정 데이터 | 로딩 시간, 로딩 중 최대 메모리, 안정화 후 메모리 |
| 반복 월 전환 | 두 월 사이 20회 왕복 | 마지막 월 표시, 캐시 예산, 장기적인 메모리 증가 |
| 빠른 월 전환 | 로딩이 끝나기 전에 10회 전환 | 대기 작업 취소, 오래된 결과 폐기, 오류 정리 |
| 다른 탭 왕복 | 정원↔다른 탭 10회 | 비활성 작업 억제, 복귀 정상, 자원 유지 정책 |
| 백그라운드 복귀 | 전환/복귀 5회 | 애니메이션·요청 상태, WebView 복귀 |
| 화면 완전 종료 | 로그아웃/재진입 5회 | 서버 재시작, renderer/인스턴스 자원 정리 |
| 파일 오류 | 한 종류를 의도적으로 실패시킴 | 나머지 모델 처리, 오류 안내, 성공 자원 정리 |
| 확대·회전 | 꽃/나무 탭, 카메라 복귀, 줌·회전 | 기존 구도와 조작 보존, 프레임 끊김 |

필수 기록: 전체 앱 및 WebView 관련 프로세스 메모리, 로딩 중 최대값, 안정화 후 값, geometry/texture 수, 현재 인스턴스 수, 파싱/캐시/큐 수, 로딩 시간, 프레임 지연, 장시간 표시 시 발열.

`renderer.info.memory`는 geometry/texture 개수이며 GPU 메모리 바이트 전체를 뜻하지 않는다. geometry를 제거해도 렌더러의 내부 자원 때문에 모든 수치가 0이 되는 것을 합격 조건으로 삼지 않는다. 초기 준비·캐시 채움 이후 같은 시나리오를 반복할 때 지속적인 증가가 없고, 활성 작업·캐시 상한이 유지되는지 확인한다. 전체 앱 메모리는 GC와 플랫폼 캐시 때문에 즉시 감소하지 않을 수 있어 안정화 구간도 함께 기록한다.

테스트용 30/60/100송이 데이터는 실제 일기에 저장하지 않는다. 기존 22개 에셋 각 한 송이 미리보기는 외형 비교용이며, 꽃 개수가 늘어나는 부하 검증과 구분한다.

```sh
# 기존 앱: 실제 월별 일기 기준
flutter run

# 전체 에셋 외형 확인: 별도 진입점
flutter run -t lib/main_garden_preview.dart

# Dart 정적 검사
flutter analyze

# Three.js 연결 코드 문법 확인 (신규 모듈도 각각 확인)
node --input-type=module --check < assets/www/main.js
```

## 8. 이번 단계의 범위

- 카메라 시점·모델 배율·안개·기본 색감은 유지한다.
- DPR 추가 축소, 그림자 품질 변경, LOD, KTX2/Draco 도입은 측정 후 별도 결정한다. 압축 에셋을 도입할 때는 해당 디코더 연결도 함께 검증한다.
- GLB 재제작은 디자이너가 담당한다. 개발자가 원본을 임의로 감량하거나 덮어쓰지 않는다.
- 메모리 상한을 기기 공통 숫자로 먼저 확정하지 않는다. 지원 기기, 꽃 개수, 개선 전후 측정으로 결정한다.
- 이 업무 분배 문서는 커밋/푸시나 실제 개선 구현 완료를 의미하지 않는다.
